# Release signing keys

Two keys, for two different questions:

- **The Android keystore** answers *"is this APK from the same author as the
  last one?"* Android enforces it: an APK signed with a different key will not
  install over an existing one.
- **The GPG key** answers *"are these the bytes the author published?"* Nothing
  enforces it; it works only because people check.

Neither is in this repository, neither is generated by any script here, and no
script prints key material. If you are reading this to recover a lost key: you
cannot. See "When a key is lost" at the end.

This is *not* the secure boot signing key, which is a third key with much
harsher consequences — see [BURN-PROCEDURE.md](BURN-PROCEDURE.md).

---

## 1. Android keystore

Goal: a signed release APK that testers can sideload, published on GitHub
Releases. **No Play Store**, so there is no Play App Signing and no upload key
— the key you make here is the one that signs what users install, forever.

### 1.1 Create it

Requires a JDK (`keytool` ships with it).

```bash
# Somewhere OUTSIDE the repository. ~/keys is a fine choice; anywhere inside
# the working tree risks a future `git add -A`.
mkdir -p ~/keys && chmod 700 ~/keys

keytool -genkeypair -v \
  -keystore ~/keys/leekwallet-release.keystore \
  -alias leekwallet \
  -keyalg RSA -keysize 4096 \
  -validity 10000 \
  -storetype PKCS12
```

Notes on the choices:

- `-validity 10000` (~27 years). Android will not let you update an app with a
  key that has expired, and you cannot renew it — you would have to ship a new
  app that users install fresh. Long is correct here.
- `PKCS12` is the standard format; the old proprietary `JKS` prints a migration
  warning on every use.
- `keytool` asks for a store password, then name/organisation fields. The
  fields are cosmetic for sideloading — put anything truthful. **Use the same
  value for the store password and the key password**; Gradle handles differing
  ones badly and PKCS12 does not really keep them separate anyway.

Then lock it down and *record the fingerprint* — it is the thing users compare:

```bash
chmod 600 ~/keys/leekwallet-release.keystore
keytool -list -v -keystore ~/keys/leekwallet-release.keystore -alias leekwallet \
  | grep -A1 'SHA256:'
```

Put that SHA-256 fingerprint in the README. It is public, and it is what lets
somebody check that release 0.4 came from whoever made release 0.1.

The key in use for this project:

### 1.2 Back it up, now, before you use it

Losing this key means every existing install must be uninstalled before anyone
can take an update. Two copies on separate physical media, both encrypted:

```bash
gpg -c --cipher-algo AES256 ~/keys/leekwallet-release.keystore
# produces leekwallet-release.keystore.gpg — put that on two USB sticks
```

Store the passphrase separately from the sticks. A password manager entry plus
a paper copy is reasonable.

### 1.3 Build a signed APK locally

The generated Android project is not tracked, so signing has to be re-applied
after every `init`. That is what `scripts/android-release-signing.sh` is for —
it writes `keystore.properties` and adds a `release` signingConfig, and it
refuses to create or print a keystore.

**Run these from the repository root.** `pnpm --dir app` resolves `app/`
relative to the current directory, and `./scripts/...` likewise — running them
from the directory where you keep your keys, or from inside `gen/android`,
fails with `ENOENT` or `ERR_PNPM_NO_IMPORTER_MANIFEST_FOUND` rather than
anything that names the real problem.

```bash
cd /path/to/leekwallet                 # the repository root, not ~/keys
pnpm --dir app tauri android init      # regenerates gen/android

export ANDROID_KEYSTORE_PATH=~/keys/leekwallet-release.keystore
export ANDROID_KEYSTORE_PASSWORD='...'
export ANDROID_KEY_ALIAS=leekwallet
export ANDROID_KEY_PASSWORD="${ANDROID_KEYSTORE_PASSWORD}"

./scripts/android-release-signing.sh
pnpm --dir app tauri android build --apk
```

Use `export` with a leading space (or `read -s`) so the passphrase does not
land in `~/.bash_history`.

**Verify the artefact, not the build files.** The script deliberately does not
claim the output is signed:

```bash
apksigner verify --print-certs --verbose app/src-tauri/gen/android/app/build/outputs/apk/universal/release/*.apk
```

The printed SHA-256 must equal the fingerprint from §1.1. If it says "not
signed" or shows a different certificate, do not publish it.

### 1.4 The four GitHub secrets

`Settings → Secrets and variables → Actions → New repository secret`:

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 ~/keys/leekwallet-release.keystore` |
| `ANDROID_KEYSTORE_PASSWORD` | the store password |
| `ANDROID_KEY_ALIAS` | `leekwallet` |
| `ANDROID_KEY_PASSWORD` | same as the store password |

The workflow decodes the first to a file and exports the other three under the
names the script expects. Note what this means: **anyone who can push a
workflow to this repo can extract that key.** For a solo project that is an
acceptable trade for reproducible releases; if that changes, sign locally and
upload the APK by hand instead.

Confirm the injection worked on the *first* CI run by checking the fingerprint
in the job log — it has never run against a real keystore.

## 2. GPG key for `SHA256SUMS`

Goal: a detached signature over `SHA256SUMS`, so a user who has your public key
can tell that the hashes — and therefore the firmware — are yours.

### 2.1 Create it

```bash
gpg --full-generate-key
```

Choose: `(9) ECC (sign and encrypt)`, then `(1) Curve 25519`, key does not
expire (`0`) or 2 years if you prefer to re-affirm it. Give a real name and the
email you publish under; that identity is what a user matches against.

Ed25519 over RSA-4096 because the signature is short, it is fast, and every
`gpg` from 2.1 onward verifies it. If you need to support genuinely ancient
tooling, use RSA 4096 instead — nothing else in this document changes.

```bash
gpg --list-secret-keys --keyid-format=long
# sec   ed25519/A1B2C3D4E5F6A7B8 2026-09-03 [SC]
#       <40-hex-character fingerprint>
```

The **full 40-character fingerprint** is what you publish. Short key ids are
forgeable and should not be used to identify a key — and note the trap: the
placeholder `A1B2C3D4E5F6A7B8` in an example is not your key. `gpg
--export-secret-keys` against a key id that does not exist prints a warning and
exports *nothing*, but the shell has already created the redirect target, so
you get an empty file that encrypts happily into a plausible-looking 85-byte
"backup". Always check the size of a backup before you trust it; a real armored
ed25519 secret key is several hundred bytes.

The key in use for this project:

```
GPG signing key (fingerprint)
2E7D83AF39ACD8A9493A2372E5D8C3021D03039E
0xoucan (LeekWalletDIY) <0xoucanxxx@gmail.com>
```

### 2.2 Back it up and make a revocation certificate

```bash
gpg --export-secret-keys --armor A1B2C3D4E5F6A7B8 > /tmp/leek-secret.asc
gpg -c --cipher-algo AES256 /tmp/leek-secret.asc   # → .asc.gpg, onto two sticks
shred -u /tmp/leek-secret.asc

gpg --output ~/keys/leekwallet-revoke.asc --gen-revoke A1B2C3D4E5F6A7B8
```

The revocation certificate is how you tell the world the key is compromised
*after* you have lost control of it — it is useless if you only make it then.
Store it with the backups.

### 2.3 Publish the public half

```bash
gpg --armor --export A1B2C3D4E5F6A7B8 > leekwallet-signing-key.asc
```

Commit that file to the repo, put the 40-hex fingerprint in the README, and
optionally upload to `keys.openpgp.org`. A key committed to the same repo it
signs is weak evidence on its own — it proves nothing against someone who
controls the repo — so also post the fingerprint somewhere with a separate
history (a social account, the release announcement).

### 2.4 Sign a release

`scripts/release.sh` produces `SHA256SUMS` and stops. Signing is by hand, on
purpose: it is the one step that should involve a human deciding that these are
the bytes they meant.

```bash
cd dist/<tag>
sha256sum -c SHA256SUMS          # check before you vouch for it
gpg --armor --detach-sign --local-user A1B2C3D4E5F6A7B8 SHA256SUMS
```

Upload `SHA256SUMS` and `SHA256SUMS.asc` to the GitHub release together.

### 2.5 What a user runs

Put this in the release notes verbatim:

```bash
gpg --recv-keys <40-hex fingerprint>          # or import the .asc from the repo
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum -c SHA256SUMS
```

`Good signature` plus `OK` on the line for the file you downloaded. A
`WARNING: This key is not certified with a trusted signature` is expected until
they sign your key locally; it is not a failure.

## 3. When a key is lost

Say so publicly and quickly — a silent key change is indistinguishable from a
compromise.

- **Android keystore lost:** you cannot recover or reissue it. Publish under a
  new key, state the new fingerprint next to the old one, and tell users they
  must uninstall before installing the new APK. Their app data is gone with the
  uninstall; for this project that is the seed, so **the notice must tell them
  to have their recovery phrase before they uninstall.**
- **Android keystore compromised:** the same, plus assume every APK signed with
  it is suspect and say which releases are affected.
- **GPG key lost:** publish a new one, signed by the old one if you still have
  it. If not, the new key is a fresh claim of identity and should be announced
  everywhere the old fingerprint appears.
- **GPG key compromised:** publish the revocation certificate from §2.2
  immediately, then a new key. Re-sign the releases you still vouch for.
