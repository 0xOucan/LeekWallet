# Android build (T29, T30)

The companion app runs on Android through the same Tauri shell as the desktop
build. Since T30 it also has a **real BLE transport** there: the `transports`
command answers `["ble"]` on Android, and the app talks to a device over
Bluetooth using the same frames, the same chunking and the same commands as on
the desktop. Serial stays desktop-only — Android has no ports to enumerate.

> **Unproven on hardware.** Everything below builds and type-checks. No phone
> was attached when it was written, so no scan, no connection, no permission
> dialog and no signature has been observed on a real device. Read "Known
> state" at the bottom before believing any of it.

## How BLE reaches Android

This is the part T29 could not do, so it is worth writing down.

btleplug's own Android support is a JNI shim over a Java driver
(`com.nonpolynomial.*`, plus vendored `io.github.gedgygedgy.*` jni-utils
classes) that has to be compiled into the APK. Tauri generates
`src-tauri/gen/android/` from `tauri.conf.json` and this repo does not track it,
so anywhere you put that Java by hand is erased by the next
`tauri android init`. Compiling btleplug in anyway would give a transport that
links, advertises itself as available, and dies at the first call with a
class-not-found. That is the trap T29 refused to walk into.

The way out is Tauri's own mechanism for shipping Kotlin next to a Rust plugin.
[`tauri-plugin-blec`](https://github.com/MnlPhlp/tauri-plugin-blec) (MIT OR
Apache-2.0) is a Tauri mobile plugin: it carries an Android library project
inside the crate and declares it from its build script with
`tauri_plugin::Builder::new(..).android_path("android")`. On Android it
implements btleplug's `Central`/`Peripheral` traits in Kotlin instead of using
btleplug's platform layer at all.

The chain, all of it automatic:

1. The plugin's build script prints `cargo:android_library_path=<its android/>`.
   Because the plugin crate sets `links = "tauri-plugin-blec"`, Cargo hands
   that to dependents as `DEP_TAURI_PLUGIN_BLEC_ANDROID_LIBRARY_PATH`.
2. Our `build.rs` runs `tauri-build`, which scans for every
   `DEP_*_ANDROID_LIBRARY_PATH` and **rewrites**
   `gen/android/tauri.settings.gradle` and `gen/android/app/tauri.build.gradle.kts`
   to `include` the plugin's project and add it as an `implementation`
   dependency.
3. Gradle builds that library module and AGP's manifest merger folds its
   `AndroidManifest.xml` — which is where the Bluetooth permissions come from —
   into the app's.

So the Kotlin does not need to survive regeneration: it is never in the
generated project to begin with, it lives in the crate, and the two generated
Gradle files that point at it are rewritten from scratch on every build. Both
carry a `DO NOT EDIT THIS FILE DIRECTLY` header, which is the same contract
this repo already keeps with `sdkconfig.*`. Nothing in `gen/` is hand-edited by
T30, and `gen/` stays git-ignored.

On the Rust side the split is a build-time feature, not a fork:
`leek-transport-ble` has `transport.rs` (btleplug, feature `ble`, desktop) and
`android.rs` (blec, feature `blec`, Android), both exposing the same
`BleTransport`. `src-tauri/src/ble.rs` and everything above it is one
implementation for both platforms. Enabling both features is a `compile_error!`
rather than a silent choice of Bluetooth stack.

## Permissions

`AndroidManifest.xml` entries arrive from the plugin's manifest, merged in by
Gradle — `BLUETOOTH_SCAN` (with `neverForLocation`) and `BLUETOOTH_CONNECT` for
API 31+, `BLUETOOTH`/`BLUETOOTH_ADMIN` below that, and a
`uses-feature android.hardware.bluetooth_le`.

They are *requested* lazily, at the first scan or connect, by `preflight()` in
`transport-ble/src/android.rs`. That is the right moment: asking on launch,
before the user has expressed any interest in a device, is the pattern that
trains people to tap Deny. What happens:

- **Not yet asked** → the plugin calls `requestPermissions`, Android shows its
  own "Allow LeekWallet to find nearby devices?" dialog. The call returns
  *false* immediately — the grant is asynchronous — so this scan fails with the
  `PermissionDenied` message and the next one succeeds. **Tap the scan button
  again after granting.**
- **Denied twice** → Android silently ignores further requests, so the plugin
  opens the app's settings page instead.
- **Either way** the failure surfaces as a message naming the permission and
  the exact settings path, never as an empty device list. An empty list and a
  denied permission are indistinguishable at the OS level, and telling someone
  their wallet is not advertising when the real problem is a dialog they
  dismissed is the worst answer this code could give.
- **Radio off** is checked separately and says so.

`ACCESS_FINE_LOCATION` is in the merged manifest because the plugin declares it,
but we pass `allow_ibeacons: false` everywhere, so it is never requested at
runtime. A wallet has no business holding a location permission it never reads.

The rationale text is Android's own dialog. Custom rationale copy would mean
forking the plugin's Kotlin; the honest description is that the pre-prompt
wording is the system's and the *post-denial* wording is ours.

No entry was added to `capabilities/default.json`: the plugin's JS commands are
never invoked from the webview, only from Rust, so the window gains no new
surface. The CSP is unchanged.

## What you need

| Piece | Version used | Notes |
| --- | --- | --- |
| JDK | Temurin 21 | A JRE is **not** enough — Gradle needs `javac`. |
| Android SDK | platform 34, build-tools 34.0.0 | Licences must be accepted. |
| Android NDK | 27.2.12479018 | Installed through `sdkmanager`. |
| Rust targets | `aarch64-linux-android` (+ the other three for a real universal APK) | |
| Node/pnpm | node ≥22, pnpm 9 | |

Install the SDK pieces (adjust the SDK path if yours differs):

```bash
export ANDROID_HOME="$HOME/Android/Sdk"
"$ANDROID_HOME/cmdline-tools/latest/bin/sdkmanager" --licenses      # interactive, once
"$ANDROID_HOME/cmdline-tools/latest/bin/sdkmanager" --install \
    "ndk;27.2.12479018" "platforms;android-34" "build-tools;34.0.0" "platform-tools"
```

A JDK without root:

```bash
mkdir -p ~/.local/lib && cd ~/.local/lib
curl -sSL -o jdk21.tar.gz \
  "https://api.adoptium.net/v3/binary/latest/21/ga/linux/x64/jdk/hotspot/normal/eclipse"
tar xzf jdk21.tar.gz && rm jdk21.tar.gz
```

Rust targets:

```bash
rustup target add aarch64-linux-android armv7-linux-androideabi \
                  i686-linux-android x86_64-linux-android
```

## Environment

Every Android command needs these four. Put them in your shell profile:

```bash
export JAVA_HOME="$HOME/.local/lib/jdk-21.0.12+8"   # or your system JDK
export PATH="$JAVA_HOME/bin:$PATH"
export ANDROID_HOME="$HOME/Android/Sdk"
export NDK_HOME="$ANDROID_HOME/ndk/27.2.12479018"
```

`NDK_HOME` must point at the *versioned* directory, not at `$ANDROID_HOME/ndk`.

## Build

```bash
cd app
pnpm install
pnpm tauri android init          # only once per checkout, see "Generated project"
pnpm android:build               # debug APK, all installed targets
pnpm android:build:arm64         # just arm64, much faster
```

Only the last of those needs the SDK and the NDK. To check that the Rust half
still cross-compiles — which is all most changes touch, and is seconds rather
than minutes — you need nothing but the Rust target:

```bash
pnpm android:check               # cargo check --target aarch64-linux-android
```

The APK lands at:

```
app/src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk
```

A debug build is large (~250 MB) because the Rust library is unoptimised and
carries debug info. A release build is a fraction of that.

## Install

```bash
adb install -r app/src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk
adb logcat -s RustStdoutStderr   # the Rust side's output
```

Or `pnpm android:dev` with a device attached, which live-reloads the frontend
from the Vite dev server.

## Testing BLE on the phone

Nothing here has been run. This is the procedure, not a report.

1. On the wallet, set **Settings → Link → BLE**. The device serves one
   transport at a time (PROTOCOL.md 3b) and does not advertise at all while it
   is in USB mode — this is the single most common reason for an empty scan,
   on any platform.
2. Turn Bluetooth on on the phone. Location does **not** need to be on: the
   scan is declared `neverForLocation`.
3. Launch the app. The status badge should read `ble`, not `mock`. If it says
   `mock`, the backend answered `transports: []` and no amount of tapping will
   help — check that the APK is the new one.
4. Tap scan. The first tap raises Android's "find nearby devices" dialog and
   the scan fails with the permission message. **Grant, then tap scan again.**
5. Pick the device, connect, and run one signing request end to end. A
   signature over BLE from the phone is the only thing that proves any of this;
   a build that installs proves nothing.

If a scan comes back empty *after* the permission is granted and the device is
in BLE mode, confirm the device is advertising at all from a laptop:

```bash
cd app/transport-ble && cargo run --bin leek-ble-probe
```

That uses the desktop btleplug backend, so a success there and a failure on the
phone isolates the fault to the Android side.

Useful log filters while doing this:

```bash
adb logcat -s RustStdoutStderr BleClient BleClientPlugin
```

## Generated project

`src-tauri/gen/android/` is **git-ignored** (it already was, in
`app/.gitignore`), and this task kept it that way. It is generated from
`tauri.conf.json` and `Cargo.toml`, so it is derived state, and committing it
would create the same trap the repo documents for `sdkconfig.*`: an edit to the
source of truth that silently does nothing because the generated file is
already there. Run `pnpm tauri android init` after a fresh clone, and re-run it
after changing the app identifier or product name.

T30 kept that decision and did **not** hand-edit anything under `gen/`. The two
files that wire the BLE plugin in — `gen/android/tauri.settings.gradle` and
`gen/android/app/tauri.build.gradle.kts` — are rewritten by `tauri-build` on
every build from the plugin's Cargo metadata. Regeneration is the mechanism,
not a hazard.

## Release signing

The debug APK is signed with the standard Android debug key and will install on
any phone with unknown sources enabled. That is all a release build needs
extra:

1. Generate a keystore **outside the repository**:
   ```bash
   keytool -genkey -v -keystore ~/leekwallet-release.jks -keyalg RSA \
           -keysize 4096 -validity 10000 -alias leekwallet
   ```
2. Create `app/src-tauri/gen/android/keystore.properties` (already ignored by
   the generated `.gitignore` — verify that before writing it):
   ```properties
   storeFile=/absolute/path/to/leekwallet-release.jks
   keyAlias=leekwallet
   storePassword=...
   password=...
   ```
3. Wire it into `app/build.gradle.kts` per the Tauri "Android code signing"
   guide, then `pnpm tauri android build`.

No keystore, password, or signing key belongs in this repository. For a wallet
the signing key is the thing that decides which binary a user's phone trusts;
treat it like `secure_boot_signing_key.pem`.
